# Паралельне обчислення суми елементів масиву

## Опис завдання

Обчислення суми елементів масиву з **1 000 000 000** елементів з розбиттям на
задану кількість частин, кожна частина рахується в окремому потоці, часткові
суми синхронно об'єднуються в загальний результат. Реалізовано на двох мовах
з вбудованою підтримкою потоків: **Go** та **Rust**. Кожна реалізація
порівнюється з однопотоковим базовим методом.

## Середовище тестування

| Параметр | Значення |
|---|---|
| Пристрій | MacBook Air, Apple Silicon (arm64), 8 логічних ядер (P+E) |
| RAM | 16 ГБ |
| ОС | macOS |
| Розмір масиву | 1 000 000 000 елементів, `int8` (1 байт ≈ 1 ГБ) |
| Заповнення | `array[i] = i % 100` (детерміноване) |
| Кількість запусків | 5 на кожен варіант, у таблиці — медіана |
| Go | 1.27.1 |
| Rust | stable, збірка `--release` |

**Чому `int8`, а не `int32`.** Перші виміри робили на `int32` (4 ГБ масив).
При такому розмірі й непорожньому фоновому навантаженні (браузер, VS Code)
macOS починала стискати пам'ять сторінками, і час гуляв у 2-3 рази між
запусками одного й того самого методу. Перехід на `int8` (1 ГБ) прибрав цей
шум. Сума все одно рахується в `int64`, задача (≥10^9 елементів) виконана.

## Реалізовані методи

### Go (4 методи)

| # | Метод | Опис |
|---|---|---|
| 1 | `sumSeq` | Базовий послідовний цикл `for range` — еталон |
| 2 | `sumWG` | Горутини + `sync.WaitGroup`, кожна пише свою суму в окрему клітинку слайсу |
| 3 | `sumChan` | Горутини шлють часткові суми в буферизований `chan int64` |
| 4 | `sumMutex` | Горутини + `sync.Mutex`, один `Lock()` на горутину наприкінці |
| — | `sumAtomicBad` | Антиприклад: `atomic.Int64.Add` на кожен елемент масиву |

### Rust (5 методів)

| # | Метод | Опис |
|---|---|---|
| 1 | `sum_seq` | Базовий послідовний `iter().sum()` — еталон |
| 2 | `sum_scope` | `thread::scope` + `spawn`/`join`, потоки безпечно позичають масив |
| 3 | `sum_channel` | Потоки шлють часткові суми через `mpsc::channel` |
| 4 | `sum_mutex` | Потоки + `Mutex`, один `lock()` на потік наприкінці |
| 5 | `sum_rayon` | Бібліотека `rayon`, `par_iter().sum()` — готовий пул потоків |
| — | `sum_atomic_bad` | Антиприклад: `AtomicI64::fetch_add` на кожен елемент |

## Аналіз ефективності

### 1. Чому базові (однопотокові) часи такі різні: 373 мс (Go) проти 20 мс (Rust)

Go-компілятор не векторизує цикл підсумовування, кожен елемент обробляється
скалярно. Rust у режимі `--release` застосовує SIMD-векторизацію (LLVM
об'єднує кілька елементів масиву в одну інструкцію), тому послідовна версія
вже читає масив із граничною для заліза швидкістю. Це видно напряму: 1 ГБ за
20 мс — це ≈50 ГБ/с, що близько до практичної пропускної здатності пам'яті
Apple Silicon.

### 2. Go: майже лінійне масштабування, потім насичення

Прискорення зростає майже лінійно до 4 потоків (373 → 102 мс, ×3.66, тобто
~91% ефективності), далі уповільнюється (8 потоків: ×6.0), а на 16 потоках
приросту немає (Mac має 8 фізичних ядер). Тут вузьке місце — обчислення
(CPU-bound): скалярний цикл не насичує шину пам'яті, тож додаткові потоки й
далі щось додають.

### 3. Rust: потоки майже не допомагають

Максимальне прискорення — лише **×1.33** (20 → 15 мс). Один потік уже working на
межі пропускної здатності пам'яті, тому додаткові потоки лише ділять ту саму
шину між собою, а не прискорюють обчислення. Це класична **memory-bound**
задача, і саме тому подальше збільшення кількості потоків (8 → 16) не дає
нічого.

### 4. WaitGroup / Channels / Mutex — однакові

У всіх трьох варіантах (в обох мовах) кожен потік рахує локальну суму й
синхронізується **один раз наприкінці**. Різниця в часі між ними — 0-3 мс,
тобто в межах шуму вимірів. Вартість каналу чи м'ютекса стає непомітною на
тлі мільйонів додавань усередині кожного потоку. Якби синхронізація
відбувалася на кожному елементі (а не раз наприкінці), різниця була б
величезною — це і показує наступний пункт.

### 5. Atomic на кожен елемент: антиприклад

Виконання `atomic.Add`/`fetch_add` на кожному елементі замість локального
накопичення дає катастрофічне сповільнення: **×90 у Go** і **×900 у Rust**.
Усі потоки постійно змагаються за одну кеш-лінію пам'яті (contention), і
атомарна операція на сучасному CPU коштує на порядки дорожче за звичайне
додавання в регістрі. Висновок: локальний накопичувач + одна синхронізація
наприкінці — обов'язковий патерн для таких задач.

### 6. Порівняння Go і Rust

| | Go | Rust |
|---|---|---|
| sequential | 373 мс | **20 мс** |
| найкращий паралельний | 62 мс (8 потоків) | 15 мс (8-16 потоків) |
| прискорення | ×6.0 | ×1.33 |
| вузьке місце | CPU (скалярний цикл) | пам'ять (вже векторизовано) |

Найкраща Rust-версія в одному потоці (20 мс) швидша за найкращу Go-версію
з 8 потоками (62 мс) утричі. Головний висновок: **розпаралелювання дає
відчутний виграш тільки тоді, коли вузьке місце — саме обчислення**. Якщо
компілятор вже сам ефективно використовує залізо (SIMD, векторизація), як у
Rust, то потоки впираються в фізичну межу пам'яті і майже нічого не дають.

---

## Загальні висновки

1. Три способи синхронізації (WaitGroup/канали, канали, mutex-раз-наприкінці)
   рівноцінні для задач без синхронізації на кожен елемент.
2. Атомарна операція на кожен елемент — антипатерн, сповільнення в 90-900 разів.
3. Прискорення від потоків залежить не від мови самої собою, а від того, чи є
   послідовна версія CPU-bound (Go) чи вже memory-bound (Rust).
4. Оптимальна кількість потоків обмежена кількістю фізичних ядер (8 у нашому
   випадку); понад це приросту немає.
5. Розмір типу елемента (`int8` замість `int32`) критично впливає на
   стабільність вимірів через тиск на оперативну пам'ять, а не тільки на
   об'єм даних.
